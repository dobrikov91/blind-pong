**PROJECT: Blind Ping Pong VR**

**Concept:** A VR ping pong game with zero visuals. Black screen. Player locates and hits a ball purely by spatial audio (3D positional sound via HRTF). Controller acts as paddle. Designed as both a fun/comedic experience and a genuine audio localization challenge.

**Core design decisions:**
- Gravity at ~40–60% of real (slower, more trackable)
- Ball speed capped so it stays locatable by ear
- No visual UI — all menus/feedback via audio/TTS
- Haptic proximity buzz on controller as ball approaches
- Training mode with ghost visual as optional onboarding

**Tech stack:**
- Engine: Unity 6 LTS
- XR: Meta XR SDK or OpenXR, Quest 2/3 target hardware
- Spatial audio: Steam Audio (HRTF + room simulation)
- Multiplayer (later phase): Photon Fusion or Unity Netcode

**Ball audio design:**
- Sharp click/tick on each bounce (primary localization cue)
- Continuous subtle whoosh on the ball during flight (trajectory tracking between bounces)
- Pitch/volume modulates with speed and distance
- Distinct sounds for: wall hit, floor/ceiling hit, paddle hit, near-miss whoosh

**Physics approach:**
- Unity Rigidbody + PhysicsMaterial (bounciness = 1, friction = 0)
- Controller velocity at moment of impact added to ball outgoing vector:
  `ball_velocity_out = reflect(ball_velocity_in, hit_normal) + controller_velocity * multiplier`
- Minimum speed floor (ball never dies), maximum speed cap

**Development phases:**
- Phase 0: Audio localization proof of concept (black scene, bouncing ball, HRTF audio only — validate the core mechanic before building anything else)
- Phase 1: Unity + Meta XR SDK + Steam Audio stack setup
- Phase 2: Physics — ball, arena box collider, controller collision with velocity transfer
- Phase 3: Spatial audio system — per-event sounds, continuous ball whoosh, proximity haptics, Steam Audio room simulation
- Phase 4: Game loop — solo rally mode, audio-only UI, training mode with ghost visual
- Phase 5: Multiplayer (later, high complexity — networked physics)
- Phase 6: Polish — sound design pass, difficulty scaling, accessibility/HRTF calibration

**Known hard problems (flag these for careful attention):**
- Controller hit feel requires playtesting to tune multipliers — code is easy, feel is iterative
- Steam Audio room simulation config is complex, docs are sparse, verify against current valvesoftware.github.io/steam-audio
- Audio-only UI/UX interaction design needs iteration, can't be fully designed upfront
- Multiplayer networked physics is the highest-risk phase — consider skipping for v1
- Sound design itself (the actual audio assets) cannot be generated by LLM — needs DAW work or a sound designer

**Start here:**
Build Phase 0 first — Unity scene, black void, Steam Audio installed, a Rigidbody sphere bouncing off box colliders with a 3D audio source attached. Verify HRTF spatial localization actually works for tracking a moving ball before writing any game logic. This is the core assumption the whole game rests on.
